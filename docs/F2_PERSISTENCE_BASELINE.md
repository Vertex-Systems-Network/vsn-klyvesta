# F2 PostgreSQL Persistence Baseline

Status: **DRAFT / stacked implementation branch**. This document does not authorize live customer data, real-money trading, personalized advice, or Guarded Auto.

Branch: `foundation/f2-postgres-persistence`
Base: `foundation/f1-dotnet-skeleton`

## Purpose

F2 establishes the smallest generic PostgreSQL persistence layer required before financial aggregates are implemented. It intentionally starts with cross-cutting correctness primitives rather than ledger/order business tables.

## Reviewed dependency baseline

As researched on 2026-08-25:

- PostgreSQL 18.6 — current supported 18.x minor release.
- Entity Framework Core 10.0.11 — current stable .NET 10 line.
- Npgsql 10.0.3 — current stable .NET/PostgreSQL driver line.
- Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 — current stable EF Core 10 provider line.
- dotnet-ef 10.0.11 — repository-local CLI tool.

No preview database/provider package is permitted in this baseline.

## Initial schemas and tables

### `ops.idempotency_record`

Purpose: persist normalized command idempotency before any externally retried financial command exists.

Critical constraints:

- application-generated UUID key;
- unique `(scope, key)`;
- fixed SHA-256 request hash representation;
- constrained lifecycle state;
- expiration must be later than creation;
- operation reference is optional until a command produces a durable operation.

A repeated idempotency key with a different normalized request hash must eventually be rejected by the application layer; the unique database key is the final duplicate-creation barrier.

### `ops.inbox_message`

Purpose: durable replay/deduplication boundary for external asynchronous events.

Critical constraints:

- unique `(provider, message_id)`;
- canonical payload hash;
- constrained processing state;
- retained received/processed timestamps;
- duplicate provider events must never produce a second financial effect.

Webhook signature verification happens before trusted processing. The inbox does not make an unsigned event trustworthy.

### `notification.outbox`

Purpose: transactional-outbox foundation for reliable internal/event/notification publication.

Critical constraints:

- event and payload persisted transactionally with future authoritative state changes;
- `attempt_count >= 0`;
- pending-row index supports worker polling;
- delivery/publishing failure never rolls back or fabricates financial truth.

## Financial data rules preserved

- no `float` / `double` authoritative money fields;
- no customer balance column is introduced;
- no broker/order/fill state is fabricated;
- no LLM/AI write path exists;
- no customer PII is required by these primitives;
- payloads must remain minimized and must not contain secrets/raw authentication tokens.

## Migration policy

- EF migrations are generated by the pinned repository-local tool and reviewed before commit;
- migrations are checked into Git;
- CI checks for pending model changes;
- CI applies migrations to an ephemeral PostgreSQL instance before acceptance;
- destructive schema operations require explicit migration/data/rollback review;
- runtime application startup will not automatically apply production migrations;
- production deployment will use a controlled migration job/bundle with separate migration credentials.

## Retry policy

Database retry is **not** a global application default.

Automatic retries can be dangerous when a transaction boundary is mixed with irreversible external side effects. Retry behavior must be operation-specific, bounded, and compatible with Klyvesta idempotency/reconciliation rules.

The design-time EF context therefore does not enable an implicit retry strategy.

## Database privilege direction

Future deployment must use separate identities for:

1. schema/migration ownership;
2. normal runtime writes;
3. read-only reporting/analytics;
4. operational break-glass access.

The runtime identity must not own schemas and must not receive unrestricted DDL privileges.

## Acceptance for this F2 increment

Before the stacked PR can be considered technically ready:

- package restore passes with NuGet audit enabled;
- formatting passes;
- Release build passes with warnings-as-errors;
- an EF migration is generated and reviewed;
- `dotnet ef migrations has-pending-model-changes` returns clean after migration commit;
- migration applies to PostgreSQL 18.x ephemeral CI database;
- duplicate idempotency key constraint is verified;
- duplicate inbox provider/message constraint is verified;
- invalid lifecycle/check-constraint writes are rejected;
- migration rollback to zero succeeds in CI for this initial generic schema;
- architecture-boundary verification still passes;
- CodeQL remains green.

## Explicitly out of scope

- identity/customer/KYC tables;
- ledger accounts/journals;
- funding/withdrawals;
- order intents/broker orders/fills;
- portfolio/mandates;
- AI decision records;
- real pyPSX adapter;
- production secrets;
- live customer data.

These are subsequent reviewed increments after the generic persistence foundation is accepted.
